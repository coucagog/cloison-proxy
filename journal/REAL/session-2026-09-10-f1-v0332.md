## 0. Doctrine produit (rappel pilote, 10/09 — PERMANENT)

**CLOISON est une passerelle OpenAI-compatible GÉNÉRIQUE.** Omarchy /
opencode / DeepSeek sont UN terrain d'essai réel parmi d'autres, jamais la
cible. Toute correction doit rester **générique** : aucun code spécifique à
un client, un SDK ou un fournisseur donné ; les comportements nouveaux sont
des comportements de protocole (aller/retour chat/completions, SSE,
`reasoning_content`, robustesse EOF/timeout, restauration), valables pour
tout client OpenAI-compatible (opencode, Codex, LibreChat, Open WebUI, SDK
maison…) et tout fournisseur (DeepSeek, GLM, OpenRouter…). Les preuves de
terrain sont des **instanciations** (ex. « DeepSeek v4 retire les
délimiteurs »), jamais des dépendances : le correctif S17 restaure les
intérieurs nus **quel que soit** le modèle qui les produit. Tests : toujours
contre un mock OpenAI-compatible générique (jamais un mock « Omarchy »).
Roadmap de compatibilité : F4 `/v1/responses`, F6 `/v1/messages` — élargir
la surface OpenAI, pas l'adapter à un client.

## 2. F1 — implémenté (code)

**Aller** (`crates/cloison-proxy/src/openai.rs`) :
- `ChatMessage.reasoning_content: Option<String>` — champ **connu** (avant :
  champ inconnu de serde, donc **silencieusement écarté** à l'aller — correction
  d'honnêteté sur le diagnostic I1(a), voir §4) ;
- tokenisé dans `engine.rs::tokenize_chat_request` exactement comme `content`
  (sidecar detect + light_ner + session, même chemin `tokenize_with_detect`).

**Retour non-stream** (`openai.rs` + `engine.rs`) :
- `ResponseMessage.reasoning_content` + restauration fail-loud dans
  `restore_chat_response` (`apply_restore`, marqueur neutre si jeton non
  résolu, compteurs agrégés).

**Retour stream** (`stream.rs`) :
- nouveau canal `delta.reasoning_content` : `BufferAndScan` dédié (mêmes
  règles de confirmation/restauration bornée que `content`), routage dans
  `process_payload`, `reasoning_event` (shape `delta.reasoning_content`),
  clôture fail-loud (`finish`) incluse dans les compteurs du flux.
- un chunk mixte `content` + `reasoning_content` route les deux canaux ;
  un chunk sans rien de routé passe tel quel (comportement inchangé).

**Audit observe-only** (`handlers.rs`) :
- `audit_count_request` compte désormais `reasoning_content` (le comptage de
  réponse était déjà récursif sur toutes les chaînes JSON).

## 4. Correction d'honnêteté sur I1(a)

Le diagnostic client « CLOISON transmet reasoning_content dans les deux sens »
était exact pour le **retour** (deltas SSE pass-through, 22 chunks vérifiés)
mais pas pour l'**aller** : `ChatMessage` sans `extra` flatten → serde écartait
silencieusement `reasoning_content` des requêtes. Le « multi-tour curl avec
replay → 200 » du client était donc nécessairement hors CLOISON. En v0.3.3.1,
**même un client conforme** (qui rejoue le champ) aurait reçu le 400.
v0.3.3.2 corrige : le champ est connu, transmis, et uniquement sous forme de
jetons. Le 400 restant côté opencode (non-replay du SDK) demeure à signaler à
opencode — consigné dans la note I1 §2.2.
