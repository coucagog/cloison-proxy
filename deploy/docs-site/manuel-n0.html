Manuel N0

Le daemon N0 : le moteur de pseudonymisation sur votre poste. L'opérateur ne lit rien — le clair ne quitte jamais votre machine, le fournisseur ne reçoit que des jetons ⟦…⟧, et la réponse vous revient restaurée. Ce manuel documente la configuration, les modes et les limites honnêtes du daemon.

01 · Ce que N0 est

N0 est un daemon local (binaire cloison-proxy en mode N0) qui expose un endpoint compatible OpenAI sur http://localhost:8787. Votre interface IA (Open WebUI, LibreChat, opencode, agents…) s'y branche avec deux champs :

Configuration client 
Base URL : http://localhost:8787/v1
Clé      : mn_<jeton_local>.<clé_amont>

Toute PII détectée est remplacée par une sentinelle ⟦…⟧ avant d'atteindre le fournisseur LLM, puis restaurée dans la réponse. La table jeton ↔ valeur (le coffre) vit chez vous, chiffrée sur disque : le fournisseur et l'opérateur ne voient jamais le clair.

L'authentification est 100 % locale : le jeton mn_ est comparé à temps constant, aucun appel au plan de contrôle n'est nécessaire pour masquer. Sans le jeton exact, le daemon répond 401 (fail-closed) et rien n'appelle le fournisseur.

02 · Installation

Le daemon est distribué en release GitHub (binaire par OS + NER léger embarqué + lib onnxruntime, checksums SHA-256 vérifiés). Aucune toolchain, aucun téléchargement de modèle à la demande.

Linux / macOS 
bash <(curl -fsSL https://raw.githubusercontent.com/coucagog/cloison-proxy/main/install-n0.sh) \
  --version v0.3.3.2

Épingler la version est la règle (--version) : le tag latest a connu des incohérences de bundle NER sur Linux. Le script crée ~/.cloison, génère la clé locataire (affichée une seule fois) et affiche la configuration à placer dans votre profil. Le détail complet (Windows, options, mise à jour, rollback) est sur la page Installer N0.

03 · Configuration

Le mode N0 s'active en posant CLOISON_VAULT_PATH — toute la configuration passe par des variables d'environnement (il n'y a pas de fichier de politique en N0) :

Shell 
export CLOISON_LISTEN_ADDR=127.0.0.1:8787           # local uniquement
export CLOISON_UPSTREAM_BASE_URL=https://api.deepseek.com/v1   # votre fournisseur
export CLOISON_VAULT_PATH=~/.cloison/vault.redb     # coffre persistant (active N0)
export CLOISON_VAULT_PASSPHRASE='votre-passphrase'  # clé du coffre, jamais persistée
export CLOISON_EXPECTED_ACCESS_TOKEN=mon_jeton_local   # jeton mn_ (sans le préfixe)
export CLOISON_TENANT_KEY_HEX=$(openssl rand -hex 32)   # clé locataire
cloison-proxy

Fail-loud au boot : passphrase absente, mauvaise passphrase ou coffre corrompu → le daemon refuse de démarrer. Jamais de recréation silencieuse du coffre, jamais de masquage dégradé sans le dire.

05 · Limites honnêtes

Limites honnêtes
Poste compromis. N0 ne protège pas contre un malware ou un vol de la machine : le coffre et la clé y vivent. La sécurité de N0 est celle de votre poste.
Texte libre sans NER léger. Sans CLOISON_NER_MODEL_ONNX, les noms hors gazetteers nom_sn/ville_sn en texte libre restent un risque de clair. Le NER embarqué (PERSON/LOC, seuil 0.70) comble ce fossé — installez-le.
PII hallucinée. Le modèle peut inventer une PII sans jeton correspondant — non résoluble par le proxy. Les sentinelles forgées ne sont en revanche jamais restaurées (registre d'émission + MAC) : elles ressortent en marqueur neutre [REDACTED], jamais en clair.
/v1/embeddings bloqué. Un embedding de PII reste dérivé de PII : la route est absente (404). Piste documentée, non livrée.
Restauration bornée à la requête. Seuls les jetons émis pour la requête en cours sont restaurés (registre + MAC) : un jeton d'une requête antérieure n'est jamais restauré. Après rotation du sel (.salt supprimé), les anciens jetons deviennent [REDACTED].

06 · Vérifier que ça marche

Shell 
curl -s http://localhost:8787/v1/chat/completions \
  -H "Authorization: Bearer mn_<jeton>.<clé_amont>" \
  -H "Content-Type: application/json" \
  -d '{"model":"x","messages":[{"role":"user","content":
       "Contact: Aminata Diop, user@example.com, tel +221 77 123 45 67"}]}'
# → la réponse contient « Aminata Diop, user@example.com, +221 77 123 45 67 »
#   (restaurés) et aucune sentinelle ⟦…⟧ résiduelle.

Le coffre ne contient aucune valeur en clair (chiffré AES-256-GCM) : grep Aminata ~/.cloison/vault.redb ne trouve rien.

07 · Coffre : sauvegarde & restauration

Trois éléments font la restaur-abilité de vos conversations : le coffre vault.redb, le sel .salt (0600, à côté du coffre) et la passphrase (dans votre tête ou le keychain OS). Sauvegardez les trois ensemble — l'un sans les autres ne restaure rien.

Shell 
# Sauvegarde (daemon arrêté) — jamais dans un cloud sans chiffrement :
cp ~/.cloison/vault.redb   ~/backups/  # coffre chiffré
cp ~/.cloison/.salt        ~/backups/  # sel de session (0600)
# la passphrase : keychain OS ou gestionnaire de mots de passe

# Restauration (nouvelle machine / après incident) :
# 1. reposer vault.redb + .salt dans ~/.cloison
# 2. redémarrer avec la même passphrase (CLOISON_VAULT_PASSPHRASE)
# 3. rejouer la sonde du §06 — les anciens jetons redeviennent restaur-ables.

Exercice recommandé (une fois) : sauvegardez, supprimez le coffre, restaurez, re-sondez. Si la restauration échoue à froid, mieux vaut le découvrir en exercice qu'en incident.
